Ownership Key — 역할 기반 5분류와 동작 방식

스펙 간 기능 중복을 예외 없이 막기 위한 소유권 키 모델. 이름이 아니라 역할(role)로 판정하고, 역할마다 실재·귀속 불변식을 강제한다. (SDD 방법론 감사 #21 반영 — 정본: DEDUP.md §3.5)

1왜 역할(role)인가

각 스펙은 ## Ownership에 자신만 소유한 키를 선언한다. 한 키는 정확히 한 스펙 — 둘이 같은 키를 소유하면 구조적 중복(결정적 게이트가 exit 1).

과거엔 판정이 카테고리 이름(/entit/ 정규식)에 걸려 있어, 이름을 Entities→Aggregates로 바꾸는 한 줄이면 강제가 조용히 죽었다(감사 A-1). 이제는 config ownershipCategoryRoles로 역할을 선언하고 모든 판정이 그 역할에 걸린다 — 이름은 자유롭고(웹 Entities, 킷 Modules), 킷 자신도 규칙을 자기에게 적용한다(도그푸딩 공백 해소, SPEC-001 FR-010).

카테고리 이름(자유)→ ownershipCategoryRoles→ 역할(entity·surface·capability·engine·event)→ 역할별 불변식 강제

2다섯 역할과 불변식

모든 소유 키는 무슨 역할인지 + 그 역할의 SSOT로 뒷받침되는지가 강제된다.

entity — aggregate root

키: 스키마 식별자 그대로 (예: pjt_projects)
구조 SSOT(스키마·마이그레이션)에 실재 + entityRegistry 등록 + 스펙당 최소 1개(entity 없는 번들 금지) + maxAggregateRootsPerSpec 이하 + 동의어·형태 변이 없음.
SPEC-026 스키마 백킹 · SPEC-002 입도 하한/상한 · SPEC-033 동의어

surface — route·화면

키: <METHOD> <path> (예: POST /api/pjt)
파일형 심볼은 소스 루트에 정방향 실재(orphan 역방향 판정의 짝).
SPEC-029 심볼 실재

capability

키: entity.verb (예: pjt_projects.create)
verb의 entity 조각을 그 스펙이 소유해야 함(귀속). cohesion 캡은 entity별로 카운트 — full-CRUD가 거짓 분할 신호를 받지 않게.
SPEC-024 귀속 · SPEC-002 entity별 캡

engine — 순수 로직

키: 모듈 식별자 (예: priceRules)
코드-모듈 SSOT(enginesSources)에 실재. capability 소유 금지(능력은 entity에 귀속).
SPEC-030 (옵트인)

event — 신호·job

키: entity.event-name (예: order.created)
발신 entity에 귀속 + 이벤트 카탈로그(eventCatalogSources)에 실재. job:를 무검증 Surface로 개명하던 우회를 봉합.
SPEC-030 (옵트인)

engine·event는 옵트인(역할 선언 전용·이름 폴백 없음) — 미선언 프로젝트는 무영향. 참조(읽기/호출만)하는 남의 entity는 ## Dependencies에 EntityName (relation-type)로 두어 dedup에서 제외한다(SPEC-017).

3동작 방식 — 키 하나가 지나는 경로

선언에서 강제까지 여섯 단계. 각 단계는 결정적(문자열 파싱·집합 대조)이라 사람 판단이 끼지 않고, 같은 입력이면 Node·Python이 바이트 동일한 판정을 낸다.

1

선언 — 스펙이 키를 소유한다

스펙 본문 ## Ownership의 카테고리 목록에 적는다. 소유 0건이면 그 자체가 위반(G1: ownershipRequiredPolicy).

## Ownership - **Modules**: entity-synonym - **Capabilities**: entity-synonym.judge
2

수집·정규화 — 표기를 하나로

parseSection이 목록을 긁고 normalizeKey가 카테고리 문법대로 접는다(METHOD 대문자, 경로 소문자, 공백 축약). 표기 차이로 중복을 놓치지 않기 위한 단계.

"post /API/Pjt" → "POST /api/pjt"
3

역할 해석 — 이름이 아니라 역할로

resolveCategoryRoles가 config 선언을 먼저 보고, 미선언이면 기존 3역할만 이름 정규식으로 폴백한다. 여기서 정해진 역할이 이후 모든 판정의 스위치다.

{"Modules":"entity","Symbols":"surface","Capabilities":"capability"}
4

판정 — 역할별 게이트가 동시에 본다

공통(유일성·교차 카테고리·Files 겹침·본문 근거) + 역할별(실재·귀속·입도·동의어). 아래 §4 탐색기에서 역할을 골라 확인.

check-ownership · check-spec-cohesion · check-synonym · …
5

회계 — 누가 판정했는지 키마다 기록

gen-ownership-map이 sdd/OWNERSHIP_MAP.md를 생성한다. 키별로 어떤 가드가 실제로 봤는지, 미판정 가드가 몇 종인지가 드러난다. 맵이 낡으면 드리프트로 exit 1.

소유 키 146건 · 미판정 가드 0종
6

강제 — 훅·CI에서 되돌릴 수 없게

pre-commit·pre-push·CI가 게이트를 돌리고, 정책 래칫(SPEC-027)이 강도 하향을 막는다. hard→advisory로 내려 회피하는 길이 닫혀 있다.

sdd-sync R1–R10 → 전부 sync ✓ | 확인 필요 → exit 1
판정했음의 증거가 남는다. 게이트는 조용히 exit 0하지 않는다 — 판정 대상 수와 결과를 항상 stdout에 찍는다(“출력 없는 통과”는 미판정으로 간주). 5단계의 맵은 그 증거를 키 단위로 모은 회계다.

4역할별 게이트 탐색기

역할을 고르면 그 키에 실제로 걸리는 게이트가 나온다. hard 차단 · advisory 경고 · opt-in 선언해야 동작.

5같은 개념·다른 이름 — 의미적 중복의 3층 (SPEC-033)

dedup은 키 문자열의 유일성만 본다. 그래서 order/orders/pjt_order처럼 형태만 다른 같은 실체, user/member처럼 말만 다른 같은 개념이 통과했다. entity 역할로 범위를 좁혀 세 층으로 나눠 잡는다.

① 형태 변이 결정적 · 차단

케이스·구분자 토큰화 + 보수적 단수화 + 선언된 접두어 제거로 정본형을 만들고, 같은 정본형을 두 키가 주장하면 충돌. status·class·analysis는 건드리지 않는다(과잉 병합이 오탐보다 나쁘다).

② 선언 동의어 결정적 · 차단

synonymRegistry에 정본·별칭·사유를 적으면, 별칭을 소유한 스펙이 지적된다. 사유 없음·별칭 0개·유령 정본·한 별칭이 두 정본에 걸림은 판정 전 즉시 에러.

③ 유사 후보 확률적 · 절대 차단 안 함

entitySimilarityCommand로 SBERT·LLM·WordNet 무엇이든 꽂는다(한 줄 = 한 후보 쌍). hard여도 미결 후보만 남으면 exit 0 — 산문 규범이 아니라 코드 분기이고 회귀 테스트로 고정돼 있다. 확률적 오탐이 빌드를 깨면 그 실수가 곧 방법론의 오류가 되기 때문이다.

↻ 미결 후보 → 사람의 결정 → 같음: synonymRegistry(정본+사유) | 다름: synonymReviewLedger(기각+사유) → 소멸
LLM은 “무엇을 볼지”만 정하고, “무엇이 참인지”는 사람이 결정적 층에 착지시킨다. 둘 다 사유가 필수라 config 리뷰 관문을 거치고, 결정 전까지 후보는 매 실행 재부상한다 — 조용한 소실이 없다. 생성기 실행 실패는 “후보 없음”이 아니라 skipped(사유)로 명시한다(오프라인에서 하드 실패 금지).

6“중복·과분류·예외 없이”의 실제 장치

목표담당 장치한계
중복 없이 키 유일성(역할·카테고리 내) + 카테고리 교차 중복(G2) + Files 글롭 겹침(G3) + 형태 변이·선언 동의어(SPEC-033) 말만 바꾼(reworded) 의미적 중복은 확률적 후보 + 사람 결정
과분류 없이 실재 불변식(스키마·심볼·모듈·카탈로그)이 유령·억지 분류 차단 + engine/event가 전수성 구멍을 담음 + 소유 선언 필수(G1) 다부모 개념은 relation 참조로 표현(단일 트리로 접지 않음)
예외 없이 강도 knob 하향 불가(단조 증가, SPEC-027 래칫 — 자기 포함). 면제는 사유 필수 + 매 실행 부채 표면화 hard 전면화 속도는 프로젝트별 graduation
예외 없이 = 하향 불가. 위반이 대량으로 떠도 정책 강도를 hard→advisory로 내려 회피할 수 없다. off·advisory는 마이그레이션 중 경유지일 뿐 종착지는 hard. 신규 채택은 hard로 태어나되, 기존 프로젝트의 소급 범람만 graduation으로 완충한다(범람 회피가 목적이지 예외가 아님).
정직한 잔여 한계. ① 형태·선언 동의어는 이제 결정적으로 잡히지만, 완전히 다른 단어로 재서술된 중복은 여전히 확률적 후보 + 사람 결정에 달려 있다(같은 entity 이웃 스펙 좁힌 ## Dedup-Review가 보조). ② 다부모(한 개념이 두 aggregate 소속)는 relation 참조로만 표현된다. ③ hard 전면 강제는 채택 속도에 달려 있다.
