Spec-Driven Development · 범용 키트

"무엇·왜"와 "어떻게"를
항상 일치시키는 개발 방법

스펙(무엇을·왜)과 코드(어떻게)를 다른 서랍에 나눠 두고, 둘이 어긋나지 않도록 기계(게이트)가 강제하고 사람이 승인한다. Spec Kit · EARS · Superpowers를 한 골격으로 묶고, 언어·모델·인프라에 무관하게 같게 돈다.

비유 — 건축 도면과 건물. 도면(spec) 없이 건물(code)을 올리면 "왜 이렇게 지었지?"를 아무도 모른다. 도면만 그리고 건물과 안 맞으면 도면이 거짓말이 된다. 이 방법론은 도면과 건물을 묶어두고, 어긋나면 경보가 울리게 한다.

이 글은 하나의 가상 기능 — "프로젝트에 직원을 추천해주는 기능" — 을 처음부터 끝까지 따라가며 설명한다. 추천 서비스가 한 모듈, 그 안의 SPEC-001이 그 기능의 명세다.

출발점

대부분은 "바이브 코딩"에서 시작했다 — prompt-driven · feature 단위

AI 개발에서 가장 흔한 방식은 바이브 코딩이다 — 말로 기능을 던지면 코드가 나오고, "돌아가 보이면" 다음으로. 빠르고 · 무계획 · 직관적이라 지배적 방식이 됐다. 문제는 작업 단위인 "feature"가 너무 굵다는 것 — 겉은 ✓ 하나여도 속의 미완성이 숨는다.

왜 이 방식인가

바이브 코딩에서 명세 기반으로

왜 바이브 코딩이 대세였고, 왜 우리는 명세 기반으로 옮겼나 — 한눈에.

실제로 무엇이 달라지나 — 같은 일, 다른 방식

바이브 코딩이 방법론
작업 단위Feature (굵음)FR — 요구 하나하나
완료 기준"돌아가 보임"unit · smoke · deferred 회계
미구현안 보임 (기억에만)deferred로 명시
추적채팅 히스토리spec ↔ code ↔ test

쉽게 말하면 — 바이브 코딩은 "말하면 바로 만들기", 이 방법론은 "무엇을 만들지 먼저 적고, 빠짐없이 만들었는지 확인하기"다.

표에 나온 말 풀이 — 요구(FR)와 "회계"

기능 요청 하나를 요구(FR) 여러 개로 쪼개고, 각 FR을 아래 셋 중 하나로 표시한다. 이 분류가 "회계(accounting)" — 셋 중 아무것도 아니면 게이트가 통과시키지 않는다. 그래서 미완성이 숨지 못한다.

unit

자동 테스트로 검증됨

그 요구를 확인하는 단위 테스트가 있고, 코드와 @covers로 묶인다 — 기계가 매번 확인.

smoke

실행 증거로 검증됨

단위 테스트 대신 실제 동작 증거(CI 로그·스크립트·runbook)로 확인. 증거에 @verifies 태그를 남긴다.

deferred

아직 안 만듦 (미룸)

일부러 뒤로 미룬 요구. 이유를 적어 미완성임을 드러낸다 — 숨기지 않고 명시.

추적 — 한 요구가 spec ↔ code ↔ test에 묶인다

단점은 있다 — 그리고 이렇게 보완했다

명세 기반이 완벽하다는 말이 아니다. SDD가 흔히 지적받는 약점을, 우리는 다음 장치로 메운다.

SDD가 지적받는 단점우리의 보완
작은 수정에도 절차가 붙는 오버헤드행위 불변(포맷팅·주석)은 Spec-Impact: none 트레일러, 행위 변경 hotfix는 /speckit.fix의 최소 스텁(Change Log 한 줄)으로 가볍게 통과
코드와 스펙을 함께 관리하는 부담retag·smoke-scan이 연결을 자동 갱신 — 손품 최소화
스펙이 낡으면 오히려 오해를 부름drift 게이트가 어긋남을 상시 감지 — 낡기 전에 되돌림
회계를 형식적으로 채울 위험근거·담당(entityRegistry) 등록을 필수화 — 빈 양식 차단
"옳은 방향"까지 게이트가 보장하진 못함마지막 판단은 사람 승인 — 기계는 정합성, 사람은 옳음
탐색 단계엔 과할 수 있음탐색은 바이브로, 굳으면 채택하는 수명주기로 설계

언제 무엇을 쓰나 — 둘은 경쟁이 아니라 단계다

바이브 코딩이 맞을 때 (탐색 · 단기)이 방법론이 맞을 때 (운영 · 장기)
프로토타입 · MVP · 해커톤 · 데모오래 유지하고 계속 커질 코드
한 번 쓰고 버릴 코드 · 아이디어 검증프로덕션 · 핵심 시스템
요구가 아직 불확실 (탐색 중)요구가 굳음 · 정확성/규정이 중요
혼자 · 단기 작업여러 사람 · 여러 모듈 협업
"빨리 돌아가는 것"이 최우선"무너지지 않는 것"이 최우선

한 프로젝트 안에서도 섞인다 — 탐색은 바이브로 빠르게 훑고, 방향이 굳으면 그 부분부터 이 방법론으로 채택한다(채택 수명주기).

한 줄로: 탐색은 바이브 코딩으로 빠르게, 굳으면 명세 기반으로 붙든다. 단점을 없앴다고 말하지 않는다 — 장치로 메우고, "옳음"은 끝까지 사람이 승인한다.
왜 필요한가

AI는 코드를 잘 짠다 — 무너지는 건 그 주변이다

LLM은 구현엔 강하다. "직원 추천 함수 짜줘"라고 하면 잘 짠다. 문제는 그 코드를 둘러싼 것들이다. 한 달 뒤 "이 추천 로직 왜 이렇게 됐지?", "이거 이미 다른 데서 만들지 않았나?", "명세엔 A인데 코드는 B인데?" — 이 셋이 시간이 지나며 반드시 무너진다. 이 방법론은 그걸 구조 + 기계적 강제로 막는 것이 전부다.

① 흩어짐

요구사항이 채팅·머릿속·주석에 흩어져 단일 진실원(SSOT)이 없다. "무엇을 만들기로 했더라?"에 답할 곳이 없다.

② 표류(drift)

핫픽스로 코드만 고치고 명세는 그대로 둔다 → 시간이 지나면 도면과 건물이 따로 논다. 명세가 거짓말이 된다.

③ 중복

이미 "추천" 기능이 있는 줄 모르고 비슷한 걸 또 만든다. 진실이 두 곳으로 갈라진다.

무엇을 조합했나

4개의 기둥

혼자 만든 게 아니라, 검증된 도구 셋을 한 골격으로 묶고 거기에 "어디서나 같게 돈다"는 보장을 더했다. 앞 3개가 무엇을 하는가, 4번째가 어디서나 같게 돈다는 약속이다.

골격

GitHub Spec Kit

specify→plan→tasks 흐름 + 리뷰 명령. "스펙의 옳음"을 담당. 30개+ 에이전트 비종속.

요구 형식

EARS

요구를 모호하지 않은 5가지 문장틀로 강제. "한 요구 = 한 동작 = 검증가능".

구현·검증

Superpowers

TDD(테스트 먼저)·완료전검증·코드리뷰. "코드의 옳음"을 담당.

보장

범용성

언어·모델·DB·클라우드·CI 무엇이든 같게. 차이는 설정 한 장으로만 흡수.

왜 한 골격으로 묶나 — 셋은 서로의 구멍을 메운다

따로 쓰면 각자 한 부분만 잘하고 구멍이 남는다. 묶어야 무엇을(EARS로 정밀히) → 관리(Spec Kit) → 검증(Superpowers) 사슬이 닫힌다 — 하나라도 빠지면 끊긴다.

혼자면

Spec Kit 단독

spec을 관리하지만 FR이 모호해도 못 막고, 코드가 맞는지 검증하지 않는다.

혼자면

EARS 단독

요구를 검증 가능하게 만들지만 문장 형식일 뿐 — 관리도 검증도 못 한다.

혼자면

Superpowers 단독

코드를 검증하지만 "무엇이 명세인가·중복인가"를 모른다.

EARS 없으면 FR이 모호해 테스트로 못 묶고, Spec Kit 없으면 명세가 흩어지고, Superpowers 없으면 코드가 미검증이라 명세가 희망사항이 된다 — 그래서 한 골격. (+ 4번째 기둥 범용성이 어디서나 같게 돌린다.)

EARS 5패턴 — 우리 예제로 보면

"직원 추천"의 요구를 EARS로 쓰면 모호함이 사라진다. 예: WHEN 직원 조회 요청이 오면, THE SYSTEM SHALL 적합도 순으로 추천 목록을 반환한다.

패턴문장틀
UbiquitousTHE SYSTEM SHALL <응답> (항상)
EventWHEN <트리거>, THE SYSTEM SHALL <응답>
StateWHILE <상태>, THE SYSTEM SHALL …
UnwantedIF <비정상>, THEN THE SYSTEM SHALL …
OptionalWHERE <옵션>, THE SYSTEM SHALL …

금지: "적절히", "가능하면", should, 한 문장에 동작 2개, 측정 불가. — 모호하면 검증할 수 없고, 검증 못 하면 게이트가 못 잡는다.

⚠ EARS는 spec 전체가 아니라 FR 절에만 적용된다. 한 spec은 여러 절로 구성되고 절마다 형식이 다르다 — 그리고 코드와 @covers로 묶이는 추적 단위는 FR뿐이다. SC·NFR은 검증·측정의 기준이지 코드에 1:1로 매달리지 않는다.

분담: FR은 이 키트의 게이트(@covers·dedup·cohesion·completeness)가 추적·강제하고, 인수조건·SC는 Spec Kit 네이티브(/analyze·/checklist·/tasks)가 담당한다. check-spec-completeness는 SC·인수조건이 존재하는지만 advisory로 지킨다 — SC 충족은 런타임 지표라 빌드 게이트가 강제할 수 없다.

선택 절 Infrastructure Prerequisites의 "왜": 인프라 의존도 요구사항이라 spec에 적되 역량으로 적는다 — "내구성 있는 이벤트 로그 필요"(O) / "Kafka"(X). spec에 두는 이유는 그 의존이 추적되고, 배포 실제(IaC)와의 drift를 검증할 수 있어서다. 인프라 의존이 없는 순수 코드 spec이면 이 절은 통째로 생략 — FR이 필수인 것과 달리 SC·NFR·Infra는 *참조(선택)*, 팀이 원하면 --strict로 강제 승격.

제일 중요 ⭐

핵심 구조

① 1 레포 = 1 모듈

레포 하나는 정확히 모듈 하나(안정적 능력 영역, bounded context)를 담는다. "추천 서비스"가 한 모듈이면 그게 레포 하나다. 모듈 안엔 여러 spec이 산다 — 추천 로직(SPEC-001), 직원 매칭(SPEC-002), 알림(SPEC-003)… 각각 한 spec.

왜 한 레포에 여러 모듈을 안 넣나? 모듈은 독립적으로 배포·교체되는 단위여야 하기 때문이다. 한 레포에 여러 모듈을 섞으면 서로 몰래 얽혀 결국 "같이만 배포되는" 덩어리가 된다. 그래서 모듈이 늘면 레포를 나눈다.

② 한 레포 안의 두 서랍

스펙(무엇/왜)과 코드(어떻게)는 다른 디렉토리에 산다. 섞으면 안 된다.

SDD 서랍 — 무엇을 / 왜
  • sdd/specs/SPEC-001.md — FR(요구) + ## Ownership
  • sdd/MODULE_MAP.md — 이 모듈의 정체성 + spec 목록
TDD 서랍 — 어떻게
  • src/recommend.ts — production 코드
  • tests/recommend.test.ts — @covers로 FR에 연결

왜 코드를 sdd/에 안 넣나? (1) 언어 테스트러너(vitest·pytest·go test)가 평범한 소스 트리에서 테스트를 찾기 때문이고, (2) 문서(명세)와 실행(코드)이 뒤섞이면 "무엇이 진실원인가"의 경계가 무너지기 때문이다. sdd/는 문서만.

③ 둘을 잇는 사슬 — @covers FR-ID (방법론의 심장)

여기가 핵심이다. 두 서랍은 딱 하나의 끈으로 묶인다 — 요구마다 붙는 번호 FR-001, 그리고 테스트에 다는 @covers 주석. 명세에 "FR-001: 추천 반환"을 쓰면, 그 요구를 검증하는 테스트에 // @covers SPEC-001/FR-001을 단다. 그러면 "이 테스트가 저 요구를 검증한다"가 기계로 추적 가능해진다.

④ sdd.config.json — "이 프로젝트의 저장·연결 방식" 한 장

그럼 게이트는 "스펙이 어디 있고, 테스트를 어디서 찾는지"를 어떻게 아는가? 이 설정 파일 하나로 안다. 그래서 언어가 Python이든 Go든 게이트 코드를 새로 짤 필요가 없다 — 값만 바꾼다.

// 언어·접두어가 달라도 게이트 코드를 새로 짤 필요 없음 — 값만 바꾼다
{
  "specDir": "sdd/specs",                  // 스펙이 어디 사나
  "specIdPrefixes": ["SPEC","INFRA","TEST","CICD"],  // 표준 4종 접두어
  "requirementIdPrefixes": ["FR"],          // 요구 ID 접두어 — 전 파싱 사이트가 이 문법 하나를 파생
  "ownershipCategories": ["Entities","Surfaces","Capabilities"],
  "scanDirs": ["src","tests"],            // @covers를 어디서 찾나
  "commands": { "test": "vitest run" }   // 게이트가 부를 언어별 명령
}

이 한 파일이 4번째 기둥(범용성)의 실체다 — 새 언어·새 스택이 와도 게이트를 새로 만들지 않고 이 값만 맞춘다.

규모가 커지면

큰 프로그램 = 여러 모듈의 MSA 합성

추천 서비스가 커져서 결제·알림까지 필요해지면? 한 레포에 욱여넣지 않고 레포를 나눈다. 추천·결제·알림이 각각 독립 모듈-레포가 되고, 사이는 공개 계약(API/이벤트 스키마)으로만 연결된다.

강제

게이트 — "주장"을 "기계적 사실"로

여기까지가 구조다. 그런데 구조를 문서로 "이렇게 합시다"라고만 적으면 사람도 LLM도 빠뜨린다. LLM은 누락을 낸다 — 그래서 확률적 리뷰가 아니라 결정적 게이트가 1차다. 게이트는 CI(또는 git 훅)에서 돌고, 규칙을 어기면 빌드를 막는다(exit 1).

같은 개념·다른 이름 — 확률적 판정에 차단력을 주지 않는 이유

dedup은 키 문자열의 유일성만 본다. 그래서 order/orders, user/member가 통과했다. entity로 범위를 좁혀 세 층으로 가른다 — 앞의 둘은 결정적이라 막고, 셋째는 정책 강도와 무관하게 절대 막지 않는다. 확률적 오탐이 빌드를 깨면 그 실수가 곧 방법론의 오류가 되고, 사람은 그 층을 통째로 떼어내기 때문이다. 미결 후보는 사람이 정본 통합 또는 기각 원장(둘 다 사유 필수)으로 결정할 때까지 매 실행 재부상한다.

실측 — 킷 entity 34건 561쌍을 전수 판정(열거는 기계, 판정은 LLM)하고, 같은 쌍에 값싼 어휘 유사도 툴이 매긴 순위를 대조했다. 툴 상위 20 진입 비율:

이름 축 (이름만 비슷)7 / 7
기능 축 (하는 일이 겹침)0 / 11

가장 중요한 쌍(live-reality ↔ runtime-schema-drift — 둘 다 “저장소 밖 진실과 대조”)에 툴은 561쌍 중 353위를 줬다. 어떤 임계값으로도 안 걸린다. 반대로 툴의 1~3위는 전부 이름만 비슷한 쌍이고 그건 ①이 이미 보는 영역이다. 그래서 외부 임베딩을 깔지 않고 후보 생성은 세션의 LLM이 맡는다(설치 0). 단 전수성은 LLM에게 맡기지 않는다 — 쌍 열거는 기계가 하고 LLM은 쌍 하나씩만 판정한다(누락은 모델 능력이 아니라 루프 구조의 문제다).

③에는 정답지가 없어 재현율을 잴 수 없다. 그래서 이 게이트는 “의미적 중복 없음”이라고 말할 수 없고 “미결 후보 없음”까지만 말한다 — 둘은 다른 문장이다. 후보 목록이 낡는 것(entity가 늘었는데 목록은 그대로)도 결정적으로 검사하지만 역시 차단하지 않는다: 커밋마다 재생성을 요구하면 사람이 ③을 떼어낸다. 상세 → · 쉬운 설명 →

초록 화면의 함정 — "검증됨"과 "아무도 안 봤음"은 다르다

위 표의 게이트들은 위반만 출력한다. 그래서 아무것도 안 나오는 화면은 두 가지를 동시에 뜻할 수 있다 — 모든 키가 검증됐다, 또는 그 판정이 애초에 돌지 않았다. 후자가 실제로 일어난다: 강도 knob이 off거나, 대조할 스키마 소스가 비어 있거나, 카테고리 이름이 달라 역할 추측이 실패하면 그 가드는 조용히 발화하지 않는다(inert). hard로 선언해 놓고 아무것도 단정하지 않는 상태가 만들어지고, 그게 가장 위험하다 — 강제한 줄 알기 때문이다.

이 규범은 오래 산문으로만 있었고, 그래서 하네스 자신이 어겼다. 게이트는 engineRealityPolicy·eventAttributionPolicy 모두 off (판정 안 함)이라고 정직하게 적었는데, 집계기는 그 줄에 ⚠·✗가 없다는 이유로 ✓ clean으로 분류했다. 문장은 사람이 읽고 분류는 기계가 하는데, 둘이 어긋나도 아무도 몰랐다. 고칠 것은 어휘가 아니라 반환 형태다 — 문자열 스캔은 새 게이트가 새 표현을 쓰는 순간 조용히 틀리고, 그 실패는 언제나 초록으로 나타난다.

게이트는 "무엇을 했는지"를 타입으로 말한다

이제 게이트는 자기 판정의 종류를 선언하고, 집계기는 그것을 읽기만 한다. 종류는 다섯 개뿐이고 늘리지 않는다 — 늘리는 순간 "이건 어디에 넣지"가 생기고, 그 자리가 곧 예외가 된다.

OFF와 INERT를 굳이 가르는 이유는 해소 방법이 다르기 때문이다 — 하나는 켜면 되고 하나는 입력을 만들어야 한다. 둘을 한 칸으로 묶으면 "켰으니 됐다"가 성립해버리고, 그게 바로 hard로 선언해 놓고 아무것도 안 보는 상태다.

그래서 스윕 화면이 세 상태로 갈린다. 그리고 요약은 언제나 분모를 밝힌다 — 초록일 때도.

● R6 정책 래칫:      ✓ 판정함
● R7 Engines·Events: · 안 봄(판정 안 함 — 통과 아님)

요약: 게이트 18종 = 판정 15 · 안 봄 3(off 2 · inert 1) · 미판정 0

이전 화면에서 R7은 ✓ clean이었다. 줄 수만 세면 18종이 전부 검증된 것처럼 읽힌다 — 실제로 검증된 것은 15종이다. "전부 sync ✓"라는 문장은 분모를 밝히지 않으면 거짓말에 가깝다.

강제의 세기는 신중히 골랐다. --strict가 막는 것은 위반과 미판정뿐이다. OFF·INERT·SKIPPED는 막지 않는다 — 채택 중인 프로젝트는 소스·매니페스트를 아직 안 갖췄고, 그 상태를 벽으로 막으면 사람이 정책을 통째로 끈다(우회를 유발하는 강제는 강제가 아니다). 대신 매 실행 집계에 남아 조용히 사라지지 않는다.

틀이 있는 것과 그 틀이 이 산출물을 본다는 것

저장소 밖을 보는 게이트(R9)는 이미 있었다. 그런데 새 배포 산출물을 선언할 때 대응 검사 등록을 요구하지 않으면 그 산출물은 여전히 아무도 보지 않는다. 실측에서 배포 산출물 결함 8건이 배포로 하나씩 발견됐다:

ECR 리포 없음 → 경로 가드 → base==HEAD → 크로스계정 ECR API →
buildx 캐시 드라이버 → 아치 불일치(arm64 노드에 amd64 이미지) →
리포 정책 부재 → 이미지에 의존 모듈 누락

전부 저장소 밖 사실이고, 전부 로컬 게이트를 초록으로 통과했다. R9 검사 항목 6건에 이 중 하나도 없었다.

정책까지 갈라야 한다는 것이 이 설계의 핵심이다. 실행은 자격증명이 없어 흔히 off이거나 훅에서 위임된다 — 한 정책에 묶여 있으면 실행을 끄는 순간 등록 누락까지 함께 안 보인다. 그게 제보가 만난 구조다. 그리고 담당 선언(covers) 없는 검사는 아무것도 커버하지 않는다: 그걸 커버로 세면 "검사가 하나라도 있으면 통과"가 되고, 그건 이 결함의 다른 이름이다.

표준 검사 4종 — 아치 일치 · 레지스트리 계정과 리포 정책 · 엔트리포인트 dry-run(이미지 안에 실제로 들어 있는가) · 스테이지 전제 자원 — 은 붙여넣을 형태로 프리셋에 있다. 프로젝트마다 다시 발명하면 같은 8건을 각자 다시 겪는다.

"단위테스트 통과"와 "배포본에서 실제 실행됨"

아치 불일치와 이미지 안 모듈 누락은 저장소 안 테스트가 100% green이어도 남는다. 깨지는 곳이 배포된 이미지의 런타임이고, 테스트는 거기 닿지 않기 때문이다. 그래서 배포 산출물을 소유한 스펙의 배포 대상 주장은 배포 등급 증거(smoke·e2e·live·runbook 또는 실행 원장 기록)를 요구한다.

⚠ 트리거는 소유와 주장 둘 다여야 한다. 마커만으로 걸었더니 킷 시운전에서 31건이 쏟아졌다 — 배포 가드의 판정 로직처럼 배포를 다루기만 하는 스펙까지 잡힌 것이고, 그런 스펙의 정답 증거는 단위테스트가 맞다. 소유 없는 마커는 화제이지 대상이 아니다.

존재는 실행이 아니다 — 조용히 사라진 검증 (규칙 R14)

같은 함정이 게이트 밖에서도 일어난다. 소비 프로젝트 실측에서 검증 절차가 세 번 조용히 사라졌다:

무슨 일이 있었나화면에는왜 안 잡혔나
에이전트가 "재현 데이터가 없다"며 실측을 중도 포기아무 일 없음포기했다는 산출물이 없다
검증 러너가 처리 대상 0건으로 exit 0성공"성공"과 "아무것도 안 함"이 같은 신호
배포 훅 Job이 참조 이미지 부재로 한 번도 안 뜸파이프라인 SUCCESS비차단 스테이지라 초록에 묻힘

[검증: <경로>]가 실재하는 자산을 지목하는지는 이미 본다(SPEC-031). 그다음 질문이 없었다 — 그 자산이 돌았는가. spec↔code 정합만 보는 층에서는 무행동과 성공이 동형이다.

그래서 실행 원장을 판정 입력으로 둔다. 러너·CI 스테이지·에이전트가 자기 결과를 남기고, 게이트는 선언된 증거와 대조한다. outcome은 위 다섯 종류를 그대로 쓴다 — 게이트와 검증 절차가 다른 어휘로 말하면 "안 봤다"가 두 뜻을 갖고, 두 뜻은 언젠가 갈라진다.

// 러너·스테이지가 남긴다 — 못 돌았으면 사유와 함께
{"asset":"tests/e2e/login.spec.ts","outcome":"JUDGED","detail":"12 passed"}
{"asset":"deploy/smoke.sh","outcome":"INERT","detail":"ECR 리포지토리 없음 — Job이 뜨지 못함"}

// 게이트 판정
선언 증거 53건 — 실행됨 52·사유 있는 미실행 1·기록 없음 0

차단하는 것은 침묵과 깨진 기록뿐이다. 기록이 아예 없으면(=안 돈 것과 구분되지 않으면) 위반이고, 사유 없이 "못 했다"만 적은 줄도 기록이 아니다. 반대로 사유가 붙은 미실행은 어떤 강도에서도 막지 않는다 — 포기는 정당하게 일어나고, 그것까지 막으면 사람이 사유를 지어내 원장이 거짓말을 담기 시작한다. 막을 것은 포기가 아니라 말 없이 사라지는 것이다.

원장은 세션·CI 로컬 상태라 커밋하지 않는다. 신선한 체크아웃에서 비어 있는 것이 정상이고, 그 비어 있음이 곧 "이 실행에서는 아직 아무것도 안 돌았다"는 참인 진술이다 — 남의 실행 기록이 내 체크아웃에서 "돌았다"로 읽히는 것이 정확히 이 층이 막으려는 거짓이다.

"0건"은 무엇의 0건인가 — 기본값은 만든 사람의 언어다

같은 함정의 다른 얼굴이 있다. 구현 중복 게이트의 기본 파일 패턴은 \.(m|c)?[jt]sx?$다 — 킷이 JavaScript로 쓰였기 때문이다. Python·Terraform으로 된 프로젝트가 이 게이트를 켜면 아무 파일도 잡히지 않아 "중복 0건"이 나온다. 그 0은 진짜 0과 구분되지 않는다.

그래서 게이트는 언어를 선언하지 않은 채 저장소 일부만 본 상태를 판정으로 치지 않는다. 무엇을 안 봤는지 지목한다:

판정: INERT — 언어 미선언 — 킷 기본(JS/TS) 패턴으로 33개만 봤고
       .md×9 .sh×7 .yml×2 .py×1 는 보지 않았다

이 검사를 켜자마자 킷 자신의 사각이 나왔다 — .py×1. 파이썬 미러(sdd_gates.py)를 구현 중복 검사가 한 번도 보지 않고 있었다. 기본값을 없애지는 않았다(그러면 기존 JS 프로젝트가 전부 INERT로 떨어져 채택이 후퇴한다) — 대신 기본값에 기대는 동안 매 실행 무엇을 안 봤는지 말하게 했다. 선언은 책임지는 행위이고, 선언하지 않은 편의에는 그 사실이 따라붙는다.

연결의 존재와 연결의 진위 — 태그가 있다는 것과 그것이 시험한다는 것

소비 프로젝트에서 스펙과 코드가 어긋난 채 모든 게이트가 초록을 유지한 사례 세 건이 왔다. 진단은 한 문장으로 모였다: 현재 게이트는 연결의 존재만 검증하고 연결의 진위는 검증하지 않는다.

세 축의 방아쇠를 고를 때 같은 기준을 썼다: 오탐이 잦은 게이트는 꺼진다. 근거 적용범위를 "관측을 주장했다"만으로 걸었더니 킷에서 77건/26스펙이 쏟아졌다 — 대부분이 "소비 프로젝트 실측"처럼 환경 무관 근거라 본 신호가 묻힌다. 관측 주장 × 환경 지목의 곱으로 좁히니 2건이고, 그 2건이 정확히 위험한 모양이었다. 용어집도 자동 추출하지 않는다(문장 첫 단어와 Title-Case가 다 걸린다) — 선언은 책임지는 행위이고, 선언하지 않은 프로젝트에는 "이 축은 판정하지 않았다"를 매 실행 말한다.

왜 소유의 입도를 줄 단위로 낮추지 않는가: 모든 상수에 요구를 붙이면 스펙이 코드의 사본이 되고, 그 순간 아무도 스펙을 읽지 않는다. 좁히는 것은 입도가 아니라 결정의 종류다 — 폴백 기본값이 외부 대상이면 그건 구현 세부가 아니라 계약이고, 계약은 스펙이 안다. 같은 이유로 EARS 문장에 범위 한정자를 문법으로 강제하지도 않는다: 이미 쓰인 수백 개 요구가 한꺼번에 위반이 되고, 그 규모의 강제는 우회를 낳는다.

세 축은 만들자마자 자기 자신을 물었다. 결정 입도 게이트는 첫 실행에서 판정 코어 자신의 설명 주석에 적힌 예시 URL을 위반으로 잡았다(→ 주석 속 예시는 인용이지 결정이 아니다. 단 줄 안쪽의 //는 절대 자르지 않는다 — "https://host"를 자르면 정확히 봐야 할 자리에서 눈이 먼다). 근거 적용범위 축을 만들며 Change Log 행 선별을 복제했더니 구현 중복 게이트(R13)가 즉시 잡았다. 그리고 자기 테스트 픽스처의 가짜 호스트가 걸렸을 때 — 면제 목록이 아니라 스펙 본문에 적어 닫았다. 픽스처라도 "이 저장소가 그 문자열을 담고 있다"는 사실은 참이고, 면제였다면 나중에 진짜 대상이 섞여 들어와도 조용히 통과했을 자리다.

지목은 배선이 아니다 (규칙 R1e)

네 번째 사례는 앞의 셋보다 훨씬 잡기 쉬웠다. FR이 배포 범위 티켓 추출의 메커니즘으로 함수를 이름으로 지목했다. 그런데 실제 표면은 그 함수를 부르지 않고 쉘로 같은 일을 다시 구현했다:

// FR-042가 지목한 메커니즘
extract every `PJT-<번호>` … deduplicate them (`extractDeployTickets()`)

// 표면(Jenkinsfile)이 실제로 한 것
DEPLOY_TICKETS=$(git log --format=%B "$RANGE" | grep -oE 'PJT-[0-9]+' | awk '!seen[$0]++')

두 구현의 규칙이 갈라졌고, 쉘 쪽에만 결함이 둘 있었다. 다건 커밋의 관행 표기 (PJT-149,133,126,…)에서 첫 건만 잡아 두 커밋에서 19건이 배포 범위에서 조용히 누락됐다(그 티켓들은 자동 실측을 한 번도 못 받았다). 그리고 근거로 인용만 한 번호가 작업 대상으로 오인됐다.

게이트는 전부 초록이었다. 커버 테스트는 있었고 표면 파일도 소유돼 있었다. 그런데 그 테스트가 단언한 것은:

expect(qa).toMatch(/DEPLOY_TICKETS=\$\(git log/)   ← 버그 있는 쉘 구현이 거기 있는지

FR이 지목한 함수가 실제로 호출되는지는 아무도 보지 않았다. 그 함수는 테스트는 통과하지만 프로덕션 경로에서 한 번도 실행되지 않는 고아 구현이었다.

여기서 이름의 출처가 결정적이다. 용어집을 자동 추출하지 않기로 한 것과 달리, 이 이름은 저자가 백틱으로 명시한 것이다 — 추측이 아니라 "이건 리터럴 이름이다"라는 저술 행위다. 그래서 선언 없이도 오탐이 없고, 한 줄 grep으로 끝난다.

백틱 스팬추출왜

deploy-tickets.mjs모듈알려진 소스 확장자를 가진다
--strict · hard · sdd.config.json · maxFRsPerSpec거부플래그·enum·config 키는 구현체가 아니다

찾는 범위는 소유 경계를 넘는다 — 라이브러리는 다른 스펙의 파일이 정당하게 소비하기 때문이다. 소유 파일 안에서만 찾았더니 킷에서 정상 모듈 3건이 거짓 고아로 떴다. 반대로 모듈이 자기 파일 헤더에 자기 이름을 적은 것은 참조로 세지 않는다 — 그걸 세면 모든 모듈이 자동으로 통과한다. 그리고 참조의 모양(import인가 언급인가)은 판정하지 않는다: import 문법을 읽으면 언어에 결합되고, 참조 0회·정의뿐이라는 가장 강한 신호만으로 실측 사례가 잡힌다.

낡은 테스트는 회귀를 막는 게 아니라 수정을 막는다

같은 사례의 뒷이야기가 하나 더 있다. 쉘 구현을 고치자 그 테스트가 깨졌다. 그 테스트의 존재 자체가 "구현이 곧 명세"가 되어버린 상태였고, 결과적으로 버그를 지키고 있었다.

테스트가 FR의 주장이 아니라 현재 구현의 형태를 단언하면 그런 일이 생긴다. 기계가 이 상태를 완전히 판정할 수는 없지만 — 의미 판정은 여전히 리뷰의 몫이다 — 값싼 신호는 있다: FR이 이름 댄 구현체가 그 FR을 커버하는 어떤 파일에도 없다. 위 사례의 테스트가 정확히 그 모양이었다.

이 판정은 의미 커버리지(R1c)의 코어를 그대로 재사용한다. 같은 대조를 두 번 구현하면 두 축이 언젠가 다른 답을 내고, 그때 사람은 어느 쪽을 믿어야 할지 모른다 — 킷이 구현 중복(R13)을 규칙으로 세운 이유가 그것이다.

사슬을 누가 소유하는가 (규칙 R16)

다섯째 사례는 앞의 넷과 층이 다르다. 한 스펙 안의 문제가 아니라 여러 스펙에 걸친 순차 프로세스의 문제다. 어떤 프로젝트의 close-out 사슬은 8단계였다:

로컬 실측 → 커밋·푸시 → main 머지 → 배포 → 개발 실측
→ 로컬·개발 교차검증 일치 → dev-done → 리포터 확인 → confirmed

조각이 6개 문서에 흩어져 있었고 전 구간을 담은 문서는 없었다. "로컬 실측"과 "교차검증"은 한 스펙에, "dev-done"과 "리포터"는 다른 넷에, "브랜치·배포 순서"는 또 다른 둘에. 어느 문서를 읽어도 사슬의 일부만 보이므로 세션마다 flow를 재구성했고, 매번 다른 곳이 빠졌다.

그리고 그 흩어짐이 코드의 무행동으로 나타났다.

if (!peers.length) return { agree: true, … };   ← 상대 기록 없으면 통과

게다가 양쪽 실행의 판정 기록이 만날 저장소가 아예 없었다 — 로컬은 작업 디렉터리, 클러스터 Job은 볼륨 없는 파드의 /tmp. 즉 그 교차검증은 단 한 번도 비교를 수행한 적이 없다. 소유자가 결정한 "교차검증 일치 시에만 전이"는 명세에만 존재했고, 저장소 요구는 어느 FR에도 없이 코드 주석에만 있었다(인프라 산출물인데 인프라 스펙 밖이라 그쪽 리뷰에서도 빠졌다).

축보는 사실해소
전 구간 소유선언된 단계가 전부 SSOT 문서 하나에 있는가흩어진 조각을 한 문서에 모은다
조각은 전체를 가리킨다단계를 둘 이상 담은 문서가 SSOT를 참조하는가그 문서에 SSOT 경로를 적는다(새 문법 없음)
비교의 만날 자리대조·합의를 요구하는 단계가 기록이 만날 저장소를 선언했고 그 저장소가 소유되는가저장소를 선언하고 어느 스펙의 Files에 편입한다

사슬을 스펙들에서 자동 재구성하지 않는다. 그러면 게이트가 사슬의 저자가 되고, 재구성이 실제 의도와 다를 때 아무도 그걸 모른다 — 사슬은 사람이 한 문서에 쓴다. 모든 단계에 저장소를 요구하지도 않는다: 대부분의 단계는 상태가 필요 없고(커밋·머지), 전부 요구하면 사람이 빈 값을 채운다. 비교·합의 마커와의 곱으로 좁혔다 — 근거 적용범위(R3)에서 방아쇠를 곱으로 좁힌 것과 같은 판단이다.

고발 장치가 고발 대상의 협조를 요구하면 그것은 강제가 아니다 (규칙 R17)

여기까지의 규칙은 모두 게이트를 돌린다는 전제 위에 있다. 그 전제가 깨지면 어떻게 되는가? 오너의 실측은 한 문장이었다 — 각 프로젝트가 방법론을 무시한다.

그 무시는 순환 때문에 잡히지 않는다. 무시하는 프로젝트는 게이트를 돌리지 않고, 그러면 게이트가 무시를 고발할 기회 자체가 없다. 고발 장치가 고발 대상의 협조를 필요로 하는 구조다.

순환을 끊는 것은 우회 불가한 채널뿐이다. 채널의 성질을 실측으로 정리하면:

채널우회 방법결론
로컬 훅--no-verify. 웹 UI 머지는 훅을 아예 타지 않는다우회 가능
게이트 파일지운다 — 지운 사실을 지운 쪽이 알린 적 없다우회 가능
서버측 CI커밋한 사람이 끌 수 없다우회 불가

그래서 "감시자가 반드시 생성된다"의 실체는 CI 배선이다. 설치기는 CI 워크플로와 채택 영수증을 선택 단계가 아니라 필수 산출물로 남기고, 그다음부터는 게이트가 그것들의 실재를 본다 — "채택했다"가 자기신고에서 기계가 읽는 사실로 바뀐다.

영수증은 커밋한다. 실행 원장(R14)은 세션 상태라 커밋하지 않지만, 영수증은 "이 저장소가 이 방법론을 채택했다"는 선언이고 체크아웃마다 사라지면 선언이 아니다. 그리고 상류 대비 낡음은 판정하지 않는다 — 네트워크 없이 알 수 없고, 모르는 것을 위반으로 말하지 않는다. 대신 채택 시점과 킷 커밋을 매 실행 그대로 보여줘 사람이 갱신 시점을 판단하게 한다.

이 규칙이 필요하다는 증거는 규칙을 만든 그 라운드에 나왔다. 어떤 소비 프로젝트가 결함 6건을 제보했는데 그중 5건이 이미 고쳐진 것이었다 — 그 프로젝트는 낡은 킷으로 몇 달을 갔고, 낡았다는 사실을 아무도 알려주지 않았다.

차단 분기가 한 번도 발화하지 않았다면 그 규칙은 검증되지 않았다

여기까지의 규칙은 모두 문서와 코드를 읽어서 판정한다. 그런데 읽어서는 원리상 보이지 않는 결함이 있다. 어떤 검증 도구에 이런 규칙이 있었다:

상대 기록 불일치 → 마감 금지  ✓ (테스트 통과)
상대 기록 일치   → 마감 허용  ✓ (테스트 통과)

명세·구현·단위테스트가 모두 정상이었다. 그런데 판정 기록의 저장 위치가 로컬은 작업 디렉터리, 클러스터 Job은 볼륨 없는 파드의 /tmp였다 — 두 기록이 만날 저장소가 아예 없었다. 즉 그 교차검증은 단 한 번도 비교를 수행한 적이 없다. 소유자 결정으로 도입된 규칙이 몇 달간 명세에만 존재했다.

결함은 배선에 있었고, 코드를 읽는 어떤 검증기도 "정상"이라 답했을 것이다. 그런데 증거는 이미 매 실행 로그에 있었다:

교차검증: 상대 환경 판정 기록 없음 — 대조 생략

"생략"이 통과처럼 읽혔고, 그 값이 몇 달간 한 번도 달라지지 않았다는 사실을 신호로 읽는 장치만 없었다. 그래서 차단 분기는 자기 발화를 원장에 남기고, 세 사실을 따로 회계한다 — 셋의 해소 방법이 다르기 때문이다.

회계뜻해소
미관측기록이 0건 — 배선이 아직 없다그 분기가 발화를 남기게 배선한다
발화 0회기록은 있는데 차단 경로가 한 번도 돌지 않았다왜 안 도는지 본다 — 제보의 결함이 이 모양이었다
단조기록이 여러 번인데 사유가 한 종류뿐값이 한 번도 달라지지 않았다면 배선이 죽었을 개연성이 높다

이 축은 어떤 강도에서도 차단하지 않는다. 원장은 세션·CI 로컬 상태라 신선한 체크아웃에서 항상 0건이고, 그 상태를 벽으로 막으면 사람이 정책을 통째로 끈다. 대신 매 실행 부채로 표면화한다 — 이 결함이 몇 달을 살아남은 이유가 정확히 "표면화되지 않음"이었다.

그리고 계측 자리를 한 곳에만 두지 않는다. 처음엔 spec-first 출구만 계측했더니 unowned 차단 경로가 기록 없이 지나가 "한 번도 안 돌았다"로 오회계됐다 — 제보가 지적한 결함 계열과 똑같은 모양이다. 모든 차단 출구를 계측하고 그 사실을 계약 테스트로 고정했다. 단 설정 문법 위반 출구는 제외한다: 그건 게이트가 판정을 시작조차 못 한 상태이고, 발화로 기록하면 원장이 "규칙이 돌았다"는 거짓을 담는다.

배선 경로를 문자열로 가정하면 게이트 전체가 조용히 무력화된다

가장 값비싼 실측이 이것이었다. 도입 프로젝트가 git worktree 기반이었고, 그래서 commit-msg·pre-commit·pre-push가 한 번도 발동한 적이 없었다. 그날의 모든 커밋이 게이트를 우회했다.

워크트리에서결과
.git파일이다 → [ -d .git ] 가드가 실패해 배선이 통째로 스킵된다
--git-dir.git/worktrees/<이름> — 훅이 없는 워크트리 전용 디렉터리
--git-path hooks공통 디렉터리의 실제 훅 자리. core.hooksPath도 함께 해결한다

--git-dir과 core.hooksPath를 손으로 합치던 방식이 바로 그 결함의 원인이었다. git에게 한 번 묻는 것이 정답이다.

그런데 이 결함을 몇 달간 가린 것은 경로 버그 자체가 아니었다. best-effort 침묵이었다 — 설치기가 "깔았다"고 말한 뒤 그 자리에 실행 가능한 훅이 실제로 있는지 세지 않았다. 이제 설치기가 배선 건수를 실측해 0건이면 실패로 말한다. 조용한 0건이 이 결함의 본체다.

절반만 새것인 설치는 게이트가 아니라 크래시를 낸다 (규칙 R18)

여기까지의 모든 규칙은 게이트가 실행된다는 전제에 서 있다. R17이 "게이트를 돌리는가"를 물었다면, 이 규칙은 한 칸 더 앞을 묻는다 — 돌리려 해도 로드가 되는가?

실측 제보는 이렇게 왔다. 어떤 프로젝트가 킷 최신화 절차를 따라 게이트를 갱신했는데, diff를 "내용이 다른 파일" 기준으로 훑는 방식이어서 공유 lib 27개가 목록에서 빠졌다. 그중 하나가 구판으로 남은 결과 다른 게이트가 판정 대신 이것을 냈다:

SyntaxError: The requested module './ownership-keys.mjs'
             does not provide an export named 'bodyBeforeOwnership'

부분 동기화다. 게이트 코드는 최신이고 lib은 구판이다. 이 상태가 기존 어떤 축에도 걸리지 않은 이유가 중요하다 — 킷에는 이미 "배포 목록의 전이 폐포" 계약이 있었는데, 그것은 파일이 배포되는가를 보고 이 결함은 배포된 파일이 요구된 export를 갖는가다. 파일은 거기 있었다. 한 칸 더 안쪽이었다.

회계뜻소비처가 받는 것
파일 없음복사 목록 누락ERR_MODULE_NOT_FOUND
export 없음부분 동기화 — 제보의 결함이 이것이다SyntaxError
확인 못 함파서가 export 집합을 확정할 수 없는 형태위반도 clean도 아니다 — 표면화하고 차단하지 않는다

이 축은 아무 게이트도 실행하지 않고 판정한다. import 그래프는 정적으로 결정 가능하고, 정적으로 결정 가능한 것을 사람에게 맡기지 않는다. 판정 시작점은 게이트 자신이 놓인 디렉터리의 모듈 전부다 — 설치 위치를 물어보지 않는다(게이트는 자기가 어디 있는지 안다). 모듈이 0건이면 INERT다: Python 런타임 전용 설치라면 정상이고, 0건은 '깨끗함'이 아니라 '볼 것이 없음'이다.

오탐이 이 축의 사망 원인이므로(오탐이 잦은 게이트는 꺼진다) 킷 전체를 교정 집합으로 먼저 재고 도입했다 — 명명 import 456건 대조, 오탐 0건. 그리고 파서가 모델하지 못하는 export 형태를 만나면 "없다"고 단정하지 않고 확인 못 함으로 자백한다. 실측 한 토막: 이 게이트를 처음 돌렸을 때 유일한 발견이 자기 자신의 주석에 있던 예시 코드였다 — 주석 속 예시는 인용이지 결정이 아니다.

크래시의 마지막 줄은 원인이 아니다

같은 제보가 부수적으로 드러낸 것. 위 SyntaxError가 났을 때 스윕이 사유로 보고한 문장은 이것이었다:

(미판정: 판정 타입 없이 비정상 종료) — Node.js v22.22.2

스윕은 게이트 출력의 마지막 줄을 요약으로 뽑았고, 크래시 stderr의 마지막 줄은 런타임 버전 배너였다. 원인 줄은 스택 프레임 위에 묻혀 있었으므로 제보자가 스택을 직접 읽어야 했다. 마지막 줄이 요약인 것은 게이트가 협조적으로 끝났을 때만 참이다 — 크래시는 협조가 아니다.

이제 요약은 스택 프레임·캐럿·버전 배너를 형태로 걸러낸 뒤 던져진 오류 줄을 고른다(특정 런타임의 어휘에 기대면 다른 런타임에서 통째로 빗나간다). 침묵이 아니라 오진이었던 사례다 — 게이트 크래시는 원래도 미판정으로 계상돼 초록이 아니었지만, 사유가 쓸모없으면 사람이 원인까지 가는 길이 없다.

감시자가 있다와 감시자가 에이전트를 본다는 다른 사실이다 (규칙 R19)

오너의 실측은 한 문장이었다 — "SDD에 의해 수행하는지 혼자 날뛰지 않는지 봐야 하는데, 그게 동작을 하지 않아."

R17이 이미 "감시자가 실재하는가"를 묻고 초록이었는데도 그랬다. 왜냐하면 R17이 보는 채널은 커밋 이후에 돈다. 관측 시점을 늘어놓으면 빈 칸이 보인다:

층언제 보는가무엇을 볼 수 있나
CI (R17)커밋·머지 이후완성된 changeset. 우회 불가하지만 사후다
git 훅 (R12)커밋 시점이미 작성된 코드. 순서 위반이 여기서 처음 드러난다
에이전트 훅 (R19)에이전트가 도구를 쓰는 순간"지금 스펙 없이 코드를 쓰고 있다" — 이걸 말할 수 있는 유일한 자리

그 세 번째 층의 배선이 어떤 축의 판정 대상도 아니었다. 그래서 아무것도 에이전트를 보지 않는 상태가 감시자 축의 초록과 공존할 수 있었다.

가장 결정적인 증거는 킷 자신이었다. 이 킷은 모든 축을 스스로에게 적용하는데 이 층만 도그푸딩이 0이었다 — .claude/ 디렉터리가 아예 없었다. 즉 이 배선이 동작하는 것을 킷이 한 번도 관측한 적이 없다. 게이트를 만들자마자 킷에서 위반 5건이 나왔고, 배선한 뒤 편집 가드가 이 킷에서 처음 실제로 발화했다.

나머지 네 원인도 모두 조용한 0건 계열이었다:

원인왜 조용했나
영수증이 git 훅만 기록"감시 에이전트가 깔렸는가"를 영수증에서 알 수 없었다 — 무엇을 깔았는지가 영수증의 존재 이유인데
jq 미설치 → 배선 스킵설치가 성공으로 끝났다. 워크트리 결함을 몇 달간 가린 침묵과 같은 모양
편집 가드 경로 하드코딩src/|lib/|app/였고 킷의 scanDirs는 tooling — 배선했어도 발화할 수 없었다
그 하드코딩의 주석"설치기가 조정한다"고 적혀 있었지만 설치기는 그 파일을 복사만 했다

훅 목록은 이제 단일 선언이다 — 설치기와 게이트가 같은 파일을 읽는다(R12에서 배운 것: 목록이 둘이면 훅을 추가해도 한쪽이 뒤처져 "설치 안 됐는데 아무도 모르는" 상태가 된다). 배선은 그 선언에서 계산되고, 실패는 큰 소리로 멈추며, 배선 직후 자기검증을 돈다. jq는 더 이상 쓰지 않는다.

매처는 부분집합으로 판정한다. 프로젝트가 감시 도구를 넓히는 것(Write|Edit → Write|Edit|MultiEdit)은 정당한 강화인데 정확 일치를 요구하면 그것이 전부 위반이 되고, 오탐이 잦은 게이트는 꺼진다. 좁혀서 어떤 도구가 감시 밖으로 나가면 그 도구를 이름으로 말한다.

자동 치유는 두지 않았다. 게이트가 설정을 직접 고쳐 배선할 수도 있었지만, 판정 게이트가 판정 대상을 고치면 그 게이트는 언제나 초록이고 초록의 의미가 사라진다. 생성 모드는 배선을 산출만 하고 쓰기는 설치기가 한다. 그리고 이 축은 배선의 실재만 판정한다 — 훅이 발동한 뒤 에이전트가 경고를 따르는지는 다른 층이고(차단 분기 발화 회계), 두 사실을 합치면 "훅이 깔렸다"가 "에이전트가 따랐다"로 읽힌다.

훅이 있어도 낡으면 없는 것과 같다

훅 배선 축(R12)은 "훅이 없으면 아무것도 발동하지 않는다"는 전제로 만들어졌다. 그 전제에 빠진 경우가 있었다 — 훅이 있는데 낡은 경우다. 실측 제보:

scripts/sdd-commit-msg.sh  (저장소본, 31행)  게이트 호출 있음
.git/hooks/commit-msg      (설치본,   26행)  그 호출 없음  ← 누락 5행이 호출 블록 전체
processCompliancePolicy = hard                게이트 직접 호출 → exit 1, 위반 3건
check-hooks-installed                         OK (선언 3종 · 설치 3종)

게이트는 옳았다. 배선이 낡았을 뿐이고, 판정이 존재·실행권한·킷 마커 3종만 봤기 때문에 배선이 빠진 사본이 "설치됨"으로 계산됐다. 그 결과 hard로 켜둔 감시 게이트가 한 번도 발동하지 못했다.

원인은 두 층이었고, 둘 다 이 킷이 이미 한 번 배운 실패의 재발이다:

층무엇이 잘못됐나같은 계열의 선례
설치기사본이 있으면 skip — 원본이 바뀌어도 갱신하지 않았다워크트리에서 훅 경로를 문자열로 가정해 조용히 skip
판정존재·권한·마커만 보고 내용 신선도를 대조하지 않았다"존재는 실행이 아니다"의 한 층 더 안쪽

판정 종류에 둘을 더했다. stale(설치본이 원본과 다르다 — 미설치와 동급으로 다룬다)과 source-unreadable(원본을 읽지 못해 신선도를 확인하지 못했다 — 통과가 아니다). 그리고 설치기는 킷 소유 사본을 내용이 다르면 항상 갱신한다.

단 모든 복사를 갱신하게 만들지는 않았다. 같은 함수가 sdd.config.json·템플릿도 옮기는데, 거기서 덮어쓰면 사용자 편집이 사라진다. 킷이 소유한 것은 갱신하고 프로젝트가 편집하는 씨앗은 보존한다 — 의미가 다른 두 복사를 한 함수에 담지 않는다.

그리고 원본 미선언과 원본 읽기 실패를 가른다. 원본이 선언되지 않은 훅은 신선도를 판정하지 않고(위반이 아니다), 선언됐는데 못 읽으면 "확인 못 함"으로 계상한다. 둘을 합치면 원본이 없는 훅 전부가 소음이 되고, 소음이 되는 순간 사람이 정책을 끈다. 미판정 훅은 매 실행 이름과 함께 표면화된다 — 안 본 것을 조용히 초록에 합산하지 않는다.

결정적인 것과 옳은 것은 다르다 — 게이트도 고장 난다

"게이트는 결정적이라 신뢰할 수 있다"는 논거는 절반만 맞다. 틀린 게이트는 틀린 답을 결정적으로 재현한다. 그리고 검증 도구의 고장은 실패가 아니라 통과로 나타나므로 일반 테스트로 드러나지 않는다 — 실측 제보에서 어떤 게이트는 티켓 19건을 흘리면서 green이었다.

그래서 스윕에 등재된 게이트는 자기 차단 능력을 증명하는 테스트를 가져야 한다. 통과 경로만 관측된 게이트는 clean이 아니라 미검증이다.

픽스처에 위반을 심어 게이트마다 실제로 돌려보는 것이 더 강하다. 그러나 게이트 22종 × 픽스처 실행은 훅에서 못 돌 무게이고, 무거운 강제는 우회를 낳는다. 그래서 차단 단언의 존재를 정적으로 요구한다 — 값싸고 결정적이며, "정적으로 결정 가능한 것은 실행·에이전트에 맡기지 않는다"는 원칙과도 맞는다. 도입 즉시 자기 사각을 잡았다: 그 라운드에 새로 만든 감시자 게이트 자신이 차단 증명 없이 등재돼 있었다(나머지 21종은 이미 있었다).

트리거 소유권도 같은 결이다. 감시 대상이 에이전트의 판단인데 감시를 에이전트가 불러야 하면, 절차를 건너뛸 때 감시도 같이 건너뛴다. 의미 판정에 에이전트가 필요하더라도 그 호출은 게이트가 강제한다 — 킷의 확률적 층이 이미 이 구조다: 어댑터를 게이트가 부르고, 그 판정에는 차단력을 주지 않는다.

하드코딩을 지양한다 — 박아 넣은 어휘는 다른 프로젝트에서 눈을 감는다

이건 규칙이 아니라 모든 규칙에 걸리는 제약이다. 언어·어휘·문서 종류·파일 배치는 프로젝트마다 다르다. 게이트가 그것을 고정하면 목록 밖 프로젝트에서 판정이 통째로 사라지고, 그 0건은 진짜 0건과 구분되지 않는다.

그래서 판정에 쓰이는 값은 전부 null 기본(= 킷 기본값을 선언)으로 두고 config로 교체할 수 있게 하며, 게이트는 자기가 무엇을 썼는지 출력에 밝힌다.

실측으로 잡힌 이식성 결함: 소개 문서 게이트가 스윕 규칙표를 tooling/sdd-sync.mjs로 고정해 읽었다. 그런데 설치기는 게이트를 scripts/에 깐다 — 소비 사이트에서는 게이트 종수 인용이 조용히 미지원 키가 되고, 문서의 정직한 숫자가 "오타난 키"로 오진됐다. 후보 경로 해석으로 고쳤고, 못 찾으면 0으로 세지 않고 미지원으로 남긴다 — 모르는 것을 숫자로 말하지 않는다.

설명이 도구보다 늦으면 그 설명은 거짓이 된다 (규칙 R15)

지금 읽고 있는 이 문서가 규칙의 대상이다. 킷은 규칙을 늘려 왔고 이 문서는 손으로 따라왔는데, 그 손이 미끄러진 자리가 실측으로 확인됐다 — 규칙표에 R14가 생겼는데 이 문서는 R13까지였고, 아무 게이트도 그 사실을 몰랐다. 문서는 어떤 축에서도 판정 대상이 아니었기 때문이다.

새로 배우는 사람은 코드가 아니라 이 문서로 방법론을 만난다. 문서가 낡으면 그 사람은 존재하지 않는 규칙 체계를 배우고, 그 오해는 조용히 오래 간다. 그래서 소개 문서는 부산물이 아니라 산출물이고, 산출물은 게이트가 본다. 세 축 전부 결정적이다:

축보는 사실
규칙 ID 커버리지규칙표의 규칙 번호가 소개 문서에 전부 나오는가 — 신설 규칙이 설명 없이 지나가지 못한다
인용 수치 검산문서가 data-sdd-count로 자원해서 올린 숫자가 실제와 같은가 — 숫자는 가장 먼저 낡고 가장 늦게 들킨다
동반 갱신규칙표를 고친 커밋에 소개 문서가 함께 있는가 — 코드 변경이 스펙을 동반하는 것과 같은 규율

현재 상태는 이 문서가 스스로 인용하고, 게이트가 매 실행 검산한다 — 규칙 18종 · 게이트 24종 · 스펙 52종. 이 숫자가 실제와 어긋나면 커밋이 막힌다.

인용 표시는 문서가 자원해서 단다. 강제로 모든 숫자를 긁으면 버전·연도·비율까지 잡아 오탐이 폭주한다(용어집 자동 추출을 거부한 것과 같은 함정). 표시하지 않은 숫자는 이 축의 판정 대상이 아니다 — 그리고 오타난 인용 키는 "확인됨"으로 읽히지 않는다: 지원하지 않는 키를 쓰면 그것 자체가 위반으로 뜬다. 조용히 통과하는 자리를 남기지 않는 것이 이 축의 요점이다.

해소 경로는 문서 편집 하나뿐이다. 면제 목록을 두지 않았다 — 문서 갱신을 면제로 넘길 수 있으면 그 면제가 곧 정상 경로가 되고, 그러면 이 규칙은 없는 것과 같다.

여기에 기존 두 장치가 함께 선다. ① exit 0 ≠ "판정했음" — 게이트가 한 줄도 출력하지 않으면 clean이 아니라 미판정으로 집계한다(이제는 종류를 선언하지 않은 것 자체가 UNTYPED로 자백된다). ② Ownership 보증 맵(sdd/OWNERSHIP_MAP.md, 생성물) — 가드별 발화 여부와 inert 사유를 표로 적고, 소유 키마다 유일성·앵커·실재 칸을 ✓ / ✗ / 면제 — 사유 / 미판정으로 채운다. 미판정 칸은 "검증됨"이 아니라 "아무도 안 봤음"을 뜻하고, 하나라도 있으면 맵 머리에 경고가 뜬다.

실측 사례: 어떤 프로젝트의 저장소 경로에 한글이 있었는데, 게이트의 진입 판정이 문자열 비교라 퍼센트 인코딩 때문에 항상 불일치 → 본체가 실행되지 않고 한 줄도 출력하지 않은 채 exit 0. 테스트 실행 정책을 hard로 켜 둔 상태로 여러 라운드 동안 아무것도 검증되지 않았고, 집계기는 그 침묵을 "clean"으로 읽었다. 킷 자신의 경로는 ASCII라 자기 검증으로는 영구히 보이지 않는 결함이었다 — 그래서 규범을 하나 세울 때마다 성격이 다른 여러 저장소에서 실측한다.

"선언한 게 진짜 있나" — 어댑터 대신 문법으로

스펙이 "나는 pjt_projects를 소유한다"고 적었을 때, 그게 실제로 있는 테이블인지 지어낸 개념인지 누가 보나? 처음엔 정규식 어댑터에 맡겼다 — 프로젝트가 "우리 스키마는 여기 있고 이 패턴으로 읽으면 된다"고 알려주는 방식이다. 유연하지만 느슨하게 쓰면 조용히 퇴화한다: 임포트문을 스키마 선언으로 세거나, 주석 처리된 옛 DDL을 읽거나, 스펙이 자기 자신을 소스로 가리키거나, 소스 목록을 비워 판정을 없애버려도 게이트는 초록이다. 그리고 표면(surface) 쪽은 정방향 판정이 아예 없었다 — "코드에 있는데 선언 안 됨"은 봤지만 "선언했는데 코드에 없음"은 아무도 안 봤다.

그래서 어댑터를 문법으로 보강했다. 문법은 저장소의 사실에 직접 대응해서 흉내 낼 수가 없다.

문법규칙왜 우회 불가인가
모듈 문법entity 키 = 그 스펙 파일명의 슬러그파일명은 저장소 사실이다. 정규식으로 만들어낼 수 없다. 스펙별로 대조하므로 두 스펙이 서로의 이름을 바꿔 가져도 잡힌다 — 키 유일성만으로는 못 잡는 뒤바뀜이다
심볼 문법표면 키 = 선언된 소스 루트 아래 실재하는 파일·디렉토리파일이 있거나 없거나 둘 중 하나다. 디렉토리도 인정한다(디렉토리 자체가 표면인 경우가 실제로 있다)

예외 목록을 만들지 않았다. 이게 핵심이다 — 불일치가 나오면 면제로 덮는 대신 데이터를 고친다: 파일명을 키에 맞추거나, 키를 실물 이름에 맞추거나, 소스 루트를 선언한다. 킷 자신에 적용한 결과 모듈 29/29 · 심볼 52/52 · 예외 0이었고, 어긋난 4건은 전부 데이터 교정으로 닫혔다(스펙 파일 2개 이름 변경 + 루트 선언 + 디렉토리 인정).

두 문법 모두 옵트인이다 — 켜지 않은 프로젝트의 출력은 한 바이트도 달라지지 않는다. 대신 hard로 켜 놓고 판정 입력을 안 준 상태(소스 루트 미선언 등)는 거짓 안전이라 차단한다. HTTP 라우트(POST /api/x)는 파일이 아니므로 이 문법의 대상이 아니고 자동으로 빠진다 — 웹 프로젝트에 오발동하지 않는다.

서식이 키의 종류를 말한다

FR 문장 안의 서식 두 개는 장식이 아니라 기계 신호다. 각각 뜻이 정해져 있고, 어긴 것은 게이트가 잡는다.

서식뜻예
백틱entity 키, 또는 그것에 종속된 것 — 컬럼·필드·enum 값. 한마디로 데이터 모델pjt_projects · automation_mode · MANUAL_REVIEW
볼드 + (E)/(S)/(C)앵커 — 이 단어가 선언된 키의 원천이다. 마커는 카테고리 머리글자pjt_projects (E) · POST /api/x (S) · staff.recommend (C)

그래서 entity 키를 백틱에 쓰는 것은 정본이고, 반대로 표면·기능 키를 백틱에 두면 위반이다 — 그쪽 정본은 앵커뿐이기 때문이다. CLI 플래그(--strict)·강도 값(advisory)·태그 문법(@covers)은 키가 아니므로 백틱을 그대로 쓴다.

원래 요구는 "굵은 글씨가 왜 굵은지 알 수 있어야 한다"였다. 규칙을 양방향으로 닫으면 그 질문에 답이 생긴다 — 남는 굵은 것은 전부 마커 달린 선언 키이고, 소유한 키는 전부 어느 FR엔가 굵게 드러나며, 그 외는 백틱이거나 평문이다.

여기서 한 걸음 더 가려다 멈춘 지점이 있다. 경로·설정 이름을 백틱에서 이탤릭으로 분리하면 "백틱은 오직 데이터 모델"이라는 더 깨끗한 규칙이 될 것 같았다. 실측해보니 그렇지 않았다 — 백틱 사용의 67%가 CLI 플래그·강도 값·태그 문법처럼 대체 표기가 아예 없는 것들이었다(**를 이탤릭으로 쓰면 렌더링이 깨진다). 즉 옮겨도 백틱은 여전히 두 가지를 뜻하므로 목표에 도달할 수 없고, 대신 세 저장소 대량 개정 · 글롭 예외 · 경로가 모노스페이스를 잃는 손실을 치른다. 그래서 하지 않기로 했다. 규범을 세울 때 "더 깔끔해 보인다"가 아니라 측정된 이득이 기준이어야 한다는 사례로 남긴다.

과대 스펙을 쪼갠 실전 기록 — 그리고 규범이 스스로 반증된 지점

한 스펙이 FR 169개 · aggregate root 6개 · 표면 38개로 자란 사례가 있었다. 게이트가 "여러 aggregate를 삼켰다"고 경고하는데, 정작 쪼개려 하면 어느 FR이 어느 aggregate 소관인지 스펙에 근거가 없었다 — FR 169개 중 124개가 굵은 앵커를 아예 갖지 않았다(정당한 통과다: 키마다 최소 1회 앵커면 충족이므로 34개 FR이 전 키를 앵커하면 나머지는 지나간다).

그래서 처음엔 "먼저 앵커 밀도를 올리고, 그 다음 쪼갠다"는 순서를 규범으로 세웠다. 실행이 이를 반증했다. 앵커는 올릴 수 없었다 — 앵커 없는 118건 중 문장에 선언 키를 실제로 지닌 것이 4건뿐이었다. 소유 키는 전체 경로인데 FR 산문은 컴포넌트 이름을 쓰기 때문이고, 경로로 펼치는 것은 표기가 아니라 재작성이다. 그런데도 분할은 성공했다 — 귀속 근거는 앵커가 아니라 FR을 한 줄씩 읽는 것이 제공했다. 규범을 고쳤다: 앵커 밀도는 선행 조건이 아니라 있으면 편한 보조 신호다.

실제로 통한 것은 세 가지였다.

무엇왜 그게 관건인가
①분할 축을 하나로 고집하지 않는다aggregate 축으로는 51%가 갈라지지 않았다. 화면·파이프라인 축을 함께 쓰자 닫혔다 — 결과는 데이터 스펙 5개 + 표면 스펙 5개 + 다른 스펙으로의 이관 11건
②조각마다 원자 커밋 + 전체 검사11개 커밋으로 나눴고, 그래서 회귀 2건을 생긴 즉시 잡아 되돌렸다. 한 번에 하면 어디서 깨졌는지 못 찾는다
③회계 보존이 성립 증거총 요구 수와 "미회계 0"이 전 구간 불변이어야 한다. 분할은 순열이니 손실이 있으면 배정이 틀린 것이다

결과: 요구 169 → 92 · aggregate root 6 → 1 · 입도 경고 11 → 10 · 총 요구 수와 미회계 0은 전 구간 불변. ⚠ 92개는 여전히 상한(50)을 넘는다 — 그러나 "1 스펙 = 1 aggregate"는 달성됐다. 두 지표를 섞어 "분할 실패"로 읽으면 안 된다. 남은 비대함은 다른 축의 문제다.

함정 둘도 기록해 둘 가치가 있다. 앵커 승계 — 옮기는 요구가 어떤 키를 유일하게 굵게 지목하고 있으면, 남는 쪽에서 다른 요구가 그 역할을 이어받아야 한다(실측 3건). 캐시 컬럼 — 자식 표를 쓰면서 부모의 집계 캐시를 함께 갱신하는 것은 그 표의 쓰기 계약 안이다. 이 기준이 없으면 거의 모든 요구가 "여러 aggregate에 걸침"으로 분류돼 분할이 불가능해 보인다.

dedup ↔ cohesion = 거울상 (핵심 통찰)

방법론의 최대 빈칸이 여기 있었다. "이 spec이 기존과 중복인가?"를 판정할 규칙이 없어 사람·LLM 판단에 맡겨 뒀고 — LLM은 누락을 낸다(→ 거짓 green). 그래서 각 spec이 자기가 소유하는 키를 선언하게 하고, "하나의 키는 정확히 한 spec만 소유"라는 집합 규칙으로 바꿨다. 판정이 "감"이 아니라 "집합 조회"가 된다. (출처: 논문이 아니라 소프트웨어공학 1차 원칙 — DDD bounded context·SSOT·집합 유일성. 1차 원칙이라 결정적이고, 그래서 CI에서 exit 1로 강제할 수 있다.)

그래서 Ownership만 필수다 (SC·NFR은 선택). 이 판정은 모든 spec이 키를 선언해야 성립한다 — 안 적은 spec은 dedup 레이더 밖이라 그 중복이 안 걸린다(미선언 1개 = 보장에 뚫린 구멍). SC·NFR 누락은 그 기능 하나의 로컬 약점이지만, Ownership 누락은 시스템 전체 중복 보장을 깬다. 비유하면 Ownership은 그 spec이 점유한 땅의 등기 — 등기가 없으면 두 spec이 같은 땅에 건물을 올려도(중복) 아무도 모른다. (미선언은 ownershipRequiredPolicy로 강도를 정한다 — 기존 프로젝트는 advisory를 경유하되 종착지는 hard이고, 래칫이 하향을 막는다. 킷 자신은 hard.)

## Ownership  ← SPEC-001이 "내가 소유한다"고 선언하는 키들
- **Entities**: pjt_projects, pjt_staff       # 도메인 객체/테이블
- **Surfaces**: POST /api/recommend           # route·화면·이벤트
- **Capabilities**: staff.recommend           # Entity×Action — entity는 이 스펙 소유(SPEC-024)

스펙의 정체성은 entity다 (SPEC-024·SPEC-023). Capability entity.verb의 entity 조각은 그 스펙이 소유한 aggregate여야 한다(## Dependencies의 참조는 읽기/호출 선언이지 귀속 근거가 아니다 — 참조 entity 위의 capability도 위반) — entity.verb의 verb만 다르면 같은 스펙의 새 FR이고, entity가 다르면 그 entity 소유 스펙 소관이다. 그래서 "entity 없이 capability만 소유하는 기술 계층 스펙"(예: budget-engine·wizard)은 태어날 수 없다 — check-ownership이 차단한다(capabilityOwnershipPolicy). 나아가 FR 문장에서 그 키의 원천 단어를 bold(키 앵커)로 적으면 — 예: WHEN POST /api/recommend, THE SYSTEM SHALL staff.recommend — 게이트가 bold ↔ 선언 키를 대조해 장식용 강조(**Fargate** 류)를 걸러낸다(frKeyAnchorPolicy). bold는 수사가 아니라 키의 앵커다.

같은 ## Ownership 데이터를 양방향으로 보면 정반대의 두 문제를 같은 도구로 잡는다:

2계층(정직). 게이트는 "키가 같은" 구조적 중복만 막는다. "말만 다른 같은 요구"(의미적 중복)는 못 잡는다 → 같은 Entity를 소유한 이웃 spec과만 좁혀서 LLM 리뷰. 100% 자동화는 불가하니, 게이트(구조)+좁힌 리뷰(의미) 2계층으로 닫는다. 단, 절차와 어휘는 문법화했다: 검토했다는 기록(## Dedup-Review — 검토한 이웃 spec ID+판정)은 completeness가 존재와 참조 실재(언급한 ID가 실재하는 spec인가)를 검사하고, entity 어휘는 entityRegistry 등록제(신설 = config 리뷰 관문)가 막는다 — 판정의 질만 사람 몫으로 남는다. 이렇게 "게이트가 판정하지 않는 것"은 전부 선언된 리뷰 경계다(METHODOLOGY.md 리뷰 경계 선언 표 — 정의되지 않은 예외 0).

"SC·인수조건이 빠진 것 같다" — 왜 그렇게 보이고, 실제로는

이 키트로 직접 만들다 보면 SC와 인수조건이 사라진 것처럼 느껴진다. 맞다 — 위 표에서 보듯 게이트·@covers 사슬·하네스가 전부 FR 중심이라 그렇게 보인다. 하지만 빠진 게 아니라 담당이 나뉘어 있다:

이 키트가 강제 — FR
  • FR ↔ test ↔ code 추적 (@covers · fr-coverage)
  • 중복 · 입도 · 완전성 (ownership · cohesion · completeness)
Spec Kit 네이티브가 담당 — 인수조건 · SC
  • 인수조건(GWT) → /tasks로 task·test화, /analyze 커버리지
  • SC 측정가능성 → /checklist

그래서 키트는 check-spec-completeness로 "FR 있는 spec엔 SC·인수조건이 존재하는가"를 advisory로 지켜 둘을 그늘에서 끌어낸다. 단 SC의 충족(예: p95 < 200ms를 실제 달성했나)은 런타임 지표라 빌드 게이트가 강제하지 않는다 — 못 하는 걸 한다고 하지 않고 정직하게 둔다. 요약: 빠진 게 아니라, FR은 키트가·인수조건/SC는 Spec Kit이 맡고, 존재는 게이트가 지킨다.

기능 하나가 흐르는 길

생애주기 — 0~8 루프

"직원 추천"을 새로 만든다면, 이 순서로 흐른다. 한 칸 한 칸이 게이트를 통과해야 다음으로 간다.

1specify"직원 추천" 한 마디 → spec (FR을 EARS로)
2clarify빈칸([NEEDS CLARIFICATION]) 질문해서 메움
3planFR ↔ 컴포넌트 매핑
4tasks2~5분 TDD 작업으로 분해
5analyze누락·모순·중복 + 게이트(ownership/cohesion)
5b리뷰 기록·승격5의 결과를 Review Log·Dedup-Review에 기록, Status: Reviewed↑ — 이 단계 없이 6으로 가면 commit-msg가 차단(SPEC-008)
6구현TDD RED→GREEN — 테스트 먼저, 통과시킴
7머지사람 PR 리뷰·승인
8converge시간 지나 drift났나 검사 → 갭 표면화
9close-out트래커 유래 작업이면 — 트래커 dev-done → 이해관계자 보고 → 리포터 confirm

양방향 동기화 — 작성은 LLM, 승인은 사람.
· 위→아래(spec→code): 사람이 spec 작성 → 미구현을 구현.
· 아래→위(code→spec, 핫픽스): 커밋 1에 소유 스펙의 최소 스텁(Edge Case/Change Log 한 줄 — /speckit.fix 정공법, spec-first hard는 핫픽스 커밋에도 그대로) → 사람이 "무슨 기능·왜"(intent) 한 줄 입력 → LLM이 코드+intent로 spec 완전 갱신 → 사람이 "정본화 vs 되돌리기" 승인. Spec-Impact: none은 행위 불변(포맷팅) 전용 — 행위를 바꾸는 핫픽스에 쓰면 남용이다. — 코드만 보고 spec을 자동으로 덮어쓰지 않는다(그러면 spec이 코드의 거울로 전락해 drift 탐지가 무의미해진다).

⑨ 완료 루프의 꼬리 — 원점 트래커 close-out. 실무 작업의 상당수는 QA/이슈 트래커에서 유래한다(예: 페이지별 QA 메모, open→done→confirmed). 그런 작업은 verify/merge로 끝이 아니라 — ①트래커 dev-done(개발자) → ②이해관계자 완료 보고(무엇·왜·어떻게+검증 경로) → ③리포터 confirm(리포터/QA)까지가 완료다. 2인 책임분리: 개발자는 confirm을 건드리지 않는다. 트래커·보고 채널은 킷에 하드코딩하지 않고 trackerCloseout config로 인스턴스화 — 외부 시스템·사람 몫이라 게이트가 아니라 규범이다.

조종석

하네스 — 이 모든 걸 "수시로" 돌린다

지금까지는 규칙·구조였다. 하지만 규칙이 있다고 사람이 매번 "아 이제 게이트 돌리고, 중복 보고, 명세 맞춰야지"를 기억할까? 안 한다. 하네스는 그 운영을 사람과 대화하며 자동으로 끌고 가는 층이다. 핵심은 — 새 판정 로직을 만드는 게 아니라, 이미 있는 게이트를 트리거하고(detect), 사람에게 묻고(ask), 행동을 잇는다(act).

규칙언제(trigger)무엇을 묻나(ask) → 행동(act)
R1 spec→codespec 바뀜"이 FR들 코드 만들/고칠까요?" → TDD 구현
R2 code→spec코드만 바뀜"기존 고칠까 / 새로 만들까 / 무시?" → specify 갱신

결정성 — 키·경계·PREFIX

Ownership 키의 결정성 — 누가 만들어도 같은 문자열

게이트는 "한 키 = 한 spec"을 비교한다. 그런데 그 키가 어떻게 만들어지는가는 규칙 없이 사람·LLM 판단에 맡겨져 있었다 — "같은 개념인데 표기가 달라" 거짓 green이 나오거나, "다른 개념인데 비슷해 보여" 차단이 누락됐다. 이 결정성 설계가 메우는 빈칸이다.

키 생성 결정 절차 — 사람·LLM이 밟으면 같은 문자열

1 spec = 1 aggregate (분리의 결정적 기준)

"무엇이 하나의 spec인가"도 결정적 기준이 필요하다. "응집 묶음"은 주관적 — 대신 aggregate root(독립적으로 생성·삭제되는 핵심 Entity)를 경계 닻으로 쓴다.

소유

한 spec = 한 aggregate root를 Ownership.Entities에 소유. 그 aggregate를 변경하는 Capability·Surface도 함께.

참조

다른 aggregate는 Dependencies로 참조(dedup 제외). 예: recommendation spec이 staff를 읽을 때.

라우팅

새 FR → 그 FR이 변경하는 aggregate 식별 → 그 owner spec 개정. owner 없으면 새 spec(새 aggregate).

세 게이트가 한 닻으로 묶인다: dedup(1 Entity=1 spec = 경계 강제) · cohesion(Entities 2개 이상 = 여러 aggregate 삼킴 경고) · Dependencies(경계 밖 참조 명시). "독립 생성·삭제되는 root"라는 조작적 정의가 "응집 묶음"보다 훨씬 결정적이고, dedup이 사후에 강제한다.

실전 예시 — 세 키의 역할 · 라우팅 · 중복 방지

추천 모듈의 SPEC-001 ## Ownership이 이렇다고 하자:

## Ownership
- Entities:     recommendation                               ← aggregate root: "무엇에 대한 spec인가" (소유 경계 · 새 spec의 유일한 근거)
- Surfaces:     POST /api/recommend/{id}, GET /api/recommend  ← 진입점: "어디로 들어오나" (route · 화면 · job · event)
- Capabilities: recommendation.create, recommendation.list   ← 동작: "그 Entity에 무슨 일" (entity × verb)
## Dependencies
- Entities:     staff                                        ← 읽기/호출만 (소유 아님 → dedup 제외)

세 키의 역할: Entity = 정체·경계(aggregate root — 새 spec을 정당화하는 유일한 키) · Surface = 진입점(그 기능에 닿는 route/job/event) · Capability = 동작(Entity×verb). Surface·Capability는 Entity에 매달리므로 그 자체로는 새 spec 사유가 아니다 — 오직 새 Entity(aggregate)만 새 spec을 낳는다.

새 요구키 판정착지

① 결정성(정규화)

표기 위장 중복 차단

② 소유 조회 라우팅

Entity 관계 — 쪼갠 aggregate 사이의 참조를 구조화 (SPEC-017)

"1 spec = 1 aggregate"는 원칙이지만 실사용은 자주 무너진다(도그푸딩 실측: 소비 프로젝트의 한 spec이 aggregate root 7개를 안고 있어 cohesion 상한을 넘김). 과대 spec을 aggregate별로 쪼개면, 쪼개진 Entity들 사이의 관계를 적을 문법이 필요하다 — 지금까지 Dependencies.Entities는 완전한 자유 텍스트라 대상의 실재·소유 spec·순환 여부를 게이트가 전혀 보지 못했다.

구조화(opt-in)

EntityName (relation-type) 괄호 표기만 구조화 관계로 인정 — 소문자 kebab 1토큰만. 괄호 없이 이름만 적으면 지금처럼 검사 없는 레거시 자유참조(하위호환).

실재·소유 spec = hard

대상 Entity를 전체 spec의 Ownership에서 자동 해석 — 못 찾으면(오타·삭제) exit 1. 소유 spec을 수동으로 안 적어도 되니 재번호·리네임에 강하다.

순환 참조 = advisory

A→B→A처럼 aggregate 간 참조가 한 방향이 아니면 경고만(차단 안 함) — 실사용에서 항상 잘못된 건 아니라서.

spec-first 강제

코드 변경은 반드시 소유 스펙을 동반한다

핫픽스 하나가 "급해서" 스펙 없이 커밋되면, 도면과 건물이 어긋난다. spec-first 게이트는 코드를 바꿀 때 같은 changeset(브랜치) 안에서 소유 스펙이 함께 갱신됐는지 commit-msg 훅에서 hard 차단한다. "소유"는 스펙의 Files glob으로 선언된다.

Files 소유매핑 — 코드 경로 → glob → 스펙

각 스펙의 ## Ownership 절에 - **Files**: <glob> 한 줄을 추가한다. 이것이 "이 코드는 이 스펙이 소유한다"는 선언이다.

커밋 분류 — 3가지로 나뉜다

커밋 종류Files glob 매치스펙 동반 필요결과
기능 변경 — spec 소유 코드 수정✓ 매치필수FR/Edge Cases/Change Log 중 하나 추가
hotfix — 버그 픽스(스펙 진짜 무관)✓ 매치트레일러 허용커밋 메시지에 Spec-Impact: none <사유>
무관 파일 — 설정·빌드 등 Files 미매치✗ 미매치불필요침묵 통과

changeset = 브랜치(top-down 흐름 보존). staged(현 커밋) ∪ base...HEAD(이전 커밋들)를 합집합으로 본다 — 스펙을 먼저 커밋하고 코드를 나중에 커밋해도 같은 브랜치면 통과. "코드를 커밋할 때마다 스펙도 같이 고쳐야"가 아니라 "브랜치 안에서 어느 커밋에든 스펙이 있으면 된다".

스펙 수명주기 — 리뷰 안 된 스펙은 코드를 이끌 수 없다

스펙 헤더 Status:는 enum이다 — Planned → Draft → Reviewed → Approved → Active → Deprecated → Removed. 차단은 화이트리스트(Reviewed 이상만 코드 주도 가능)라 Draft만이 아니라 Planned·enum 밖 값도 걸린다(감사 T2). 강제하는 것은 시간 순서가 아니라 상태 순서다:

1Draft작성 중 — Reviewed 미만(Planned·enum 밖 포함)이 소유한 코드 변경은 commit-msg가 차단(스펙을 같이 고쳐도)
2Reviewed/analyze+/checklist 결과를 ## Review Log(일시·수행자·판정)와 ## Dedup-Review(이웃 검토)에 기록해야 승격 — 기록 존재를 completeness가 검사
3Approved → Active승인 후 구현 — 이때부터 소유 코드가 자유롭게 흐른다(동반 변경 규칙은 그대로)

미소유 파일 정책(specSyncUnownedPolicy): 어느 스펙의 Files에도 안 잡히는 변경 파일은 원래 침묵 통과였다 — 이제 silent(현행)/warn/error(closed-world) 중 하나를 선언한다. 의도적 예외는 specSyncExemptGlobs로. 검증 회계(requireAccounting): 커버 안 된 FR이 경고 속에 쌓이는 것도 막는다 — 모든 FR은 unit(@covers) ∨ smoke(매니페스트 evidence) ∨ deferred(매니페스트 reason)로 회계되어야 하고, 게이트는 사유의 존재만 강제한다(질은 리뷰 몫). Status 없는 레거시 스펙·기본값 config는 전부 현행 동작 그대로다(점진 도입 — advisory→strict 승격 경로).

Draft 차단의 사각지대 — 웹 UI 병합은 로컬 훅을 안 탄다 (draftBlockPolicy, SPEC-008 FR-007)

위 Draft 차단은 설계상 --staged(commit-msg 훅) 모드에서만 hard고, range 모드는 항상 advisory였다. 그런데 GitHub/GitLab의 웹 UI "Merge" 버튼은 로컬 git 훅을 절대 실행하지 않는다 — 로컬 클론에 훅이 설치돼 있어도 무관하다. 도그푸딩에서 실측: Draft 상태 spec이 소유한 Jenkinsfile이 Merge branch '...' into 'main' 병합 커밋으로 여러 차례 새어나갔고, 그 리포의 CI엔 게이트 호출 자체가 없어 range advisory조차 돌지 않았다. "채택 = 상시 강제"가 실제로는 로컬 커밋 경로에만 성립했던 것.

draftBlockPolicy: "advisory"(기본)

하위호환 — range 모드는 지금처럼 경고만, exit 0.

draftBlockPolicy: "hard"

range 모드에서도 Draft 위반이 exit 1. CI가 <GATE> specsync [base]를 MR 파이프라인에 걸면, 로컬 훅이 안 타는 웹 UI 병합도 이 지점에서 막힌다.

로컬 pre-push/commit-msg 훅과 이 CI 스텝은 서로를 대체하지 않는다 — 훅은 로컬 커밋 경로의 백스톱, 이 스텝은 훅이 절대 닿지 않는 서버측 병합 경로의 백스톱이다. 둘 다 있어야 "채택 = 상시 강제"가 실제로 완성된다. 킷 자신도 이 처방을 따른다 — .github/workflows/sdd-gates.yml(CICD-001)이 push/PR마다 스위트·게이트를, PR엔 range spec-sync(draftBlockPolicy: hard)를 강제한다.

재도출 소스 회계 — 재생성은 src만 읽으면 미완성이다

두 프로젝트 재생성 비교에서 [검증]된 결론: 재생성은 레포 안에서 도출 가능한 모든 것을 손작성본보다 잘 뽑지만, 초기 재도출이 src 밖(terraform/k8s/CI)을 아예 안 읽어 INFRA FR을 잃었고, smoke 실증거·@covers 재연결·인간 의도는 수작업으로 남았다. 그 4개 잔여를 전부 문법화했다:
